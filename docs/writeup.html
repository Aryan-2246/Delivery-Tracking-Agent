The Double-Booking Problem

Two riders tap “request” at the same instant, in the same place. The nearest-driver search returns the same car to both. Here is how to make sure only one of them gets it — and how to prove it.

01 · The race

The window is seconds, not microseconds

The obvious fix — guard the final database write — is too late. The gap that matters is the several seconds a human spends looking at an offer before tapping a button. Two dispatch loops can both sit inside that gap holding the same driver.

Without a lock

rider B
GEOSEARCH → driver 7
GEOSEARCH → driver 7
send offer to driver 7
send offer to driver 7

ride A ← driver 7
ride B ← driver 7
one driver, two live rides

02 · The fix

Claiming is one atomic operation

A driver is claimed before the offer is ever shown, with a single Redis command: 

SET lock:driver:<id> <rideId> NX PX 8000

NX means set-only-if-absent. Redis executes commands one at a time, so of N concurrent claims on one driver, exactly one returns OK. The losers get nil immediately and move to their next candidate — no queueing, no blocking, no retry storm.

With the lock

rider A
rider B
SET NX driver:7 → OK
SET NX driver:7 → nil
ZREM from search index
next candidate: driver 9
offer → driver 7
SET NX driver:9 → OK
accepted → ride A
accepted → ride B
two riders, two drivers, no contention

Four properties that make it hold

  1. The lock precedes the offer. Locking on accept would leave the human-decision window unguarded — which is exactly where the race lives.
  2. A claimed driver leaves the search index. ZREM on the geo set means concurrent searches never see them as a candidate. Contention is avoided rather than merely resolved.
  3. Every lock has a TTL. If the process dies between locking and offering, the driver frees themselves instead of being stranded. On accept the lock is PERSISTed for the length of the ride.
  4. Release is compare-and-delete. A bare DEL carries a subtle bug: ride A’s lock expires, ride B legitimately claims the driver, and A’s late unlock frees B’s driver out from under it.
-- release only if we still own it
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0

03 · Defence in depth

Postgres is the backstop

Redis is the fast path. The durable guarantee is a partial unique index — even if Redis were flushed, restarted, or a lock expired mid-flight, the database physically cannot record two live rides for one driver. 

CREATE UNIQUE INDEX rides_one_active_per_driver
  ON rides (driver_id)
  WHERE driver_id IS NOT NULL
    AND status IN ('matched', 'in_progress');

The write fails, the dispatcher treats it as a lost race, and moves on.

04 · Proof

A test that never fails proves nothing

So the locking can be switched off on purpose. Running the identical suite against a build with no locking produces exactly the expected damage: 

  PASS  no driver assigned to more than one live ride   ← backstop held
  FAIL  redis locks agree with postgres assignments
  FAIL  all 10 available drivers were matched           ← matched 6 of 10

And the server log shows the database catching a real double-booking:

[dispatch] backstop fired: driver 86c3932b… already has a
           live ride (rejected by rides_one_active_per_driver)

Each layer does a different job, and you can watch each one work. With locking off, correctness survives — but throughput collapses, and four of ten drivers go to waste.

05 · What the load test found

Safety held. Liveness didn’t.

At 300 riders against 40 drivers, nothing was double-booked — and only 24 drivers got matched. Sixteen sat free while riders were told nobody was available.

The dispatch loop was capping drivers examined, counting two very different things against one budget: an offer that gets refused costs up to the full offer timeout, while a lost lock race costs one Redis round-trip. Under contention a rider burned all five attempts losing races to faster riders, then gave up — with free drivers one position further down the list.

Why the liveness assertion exists

Every safety assertion in the suite is trivially satisfied by a system that refuses to match anyone. “All available drivers were matched” is the check that keeps the other six honest — and it is the one that caught this.

UNIQUE INDEXone active ride per driver

Postgres holds what must survive a restart and be auditable afterwards. Redis holds what is written several times a second per driver and worthless a minute later. Three properties make it the right home: GEOSEARCH is a real nearest-neighbour query over geohash-encoded scores rather than a table scan; SET NX gives atomic claiming for free; and availability is set membership, so the hot query never filters out busy drivers — they simply aren’t there.

A position tick costs two Redis reads and zero database queries. At 500 drivers pinging every second, routing that through Postgres would be 500 queries per second of pure overhead.

Surviving a restart

Redis runs without persistence, so a restart wipes every lock while Postgres keeps every in-flight ride. Left alone, a driver already carrying a rider would look unlocked and could be offered a second ride — the backstop would refuse the write, but only after the rider had been promised a car. So the durable record wins at boot: every live ride is read back from Postgres and its lock rebuilt before the first request is served.

08 · Next

What I’d add, and why it isn’t here

  • Multi-node dispatch. The locking is already multi-node safe — it lives in Redis. Offer routing isn’t: the socket hub is in-process, so a driver on node B can’t receive an offer dispatched on node A. A Redis pub/sub fan-out keyed by driver id fixes it, and nothing above that interface changes.
  • Real routing. ETAs are straight-line over an assumed speed, so a driver across a river reads as thirty seconds away. OSRM or Valhalla replaces one function — points in, seconds out.
  • PostGIS. Redis stores points; ride history wants real geometry, spatial joins and polygon containment. That belongs on the historical data, not the hot path.
  • Kafka. The moment billing, payouts or fraud scoring need to react to a completed ride, bolting each into the request path is how services rot. Emit lifecycle events; let consumers subscribe.
  • Global assignment. Dispatch is strictly nearest-first. Batching requests over a short window and solving an assignment problem beats greedy matching at surge — greedy is right at this scale and wrong at city scale.
  • A reaper for abandoned rides. If a driver vanishes mid-trip the ride sits in in_progress forever. I hit this for real in testing.
Express · Postgres · Redis · WebSockets — no Kafka, no PostGIS, no routing engine.
